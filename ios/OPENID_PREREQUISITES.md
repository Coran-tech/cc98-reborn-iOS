# 原生 iOS OpenID 配置与长期登录

当前 App 直接使用原生 OpenID 会话访问 CC98 API。系统授权后，以官方 `/me` 返回的身份建立账号，不要求先在旧 WebView 登录再做同账号绑定。

## 现有客户端可以继续使用

已登记并确认保存的 iOS 回调为：

```text
org.cc98.reborn.shell:/oauth/callback
```

冒号后只有一个斜杠，末尾没有斜杠。保留原浏览器扩展回调及 `https://www.cc98.org/`；无需为本轮另建客户端或购买域名。原生令牌请求不受浏览器 CORS 规则约束，不把 App scheme 填成浏览器 CORS 来源。

| 配置 | 原生客户端使用方式 |
| --- | --- |
| Client ID | `9ca359c2-4112-44de-6177-08debd80dfb1` |
| 授权端点 | `https://openid.cc98.org/connect/authorize` |
| 令牌端点 | `https://openid.cc98.org/connect/token` |
| 资料端点 | `https://api.cc98.org/me` |
| 授权方式 | Authorization Code + PKCE S256 |
| 原生请求范围 | `openid profile cc98-api read-user-info offline_access` |
| 用户同意 | 原生长期登录请求所需同意；新增范围可能需要一次重新授权 |
| 强制 PKCE | 保持开启 |
| 明文 PKCE | 保持关闭 |
| 客户端密钥 | 不使用，不打包进 App |
| 通过浏览器取得访问令牌 | 保持关闭；回调接收授权码，不接收 Bearer token |

原有 `openid profile cc98-api read-user-info` 用途不变，只为原生持续业务访问申请 `offline_access`。旧网页摘要绑定仍保留原授权范围，不被本轮扩展为长期会话。

## 后台截图已经确认的条件

| 页面显示 | 对长期登录的影响 |
| --- | --- |
| `offline_access` 已勾选 | 客户端页面允许申请离线访问；实际能否取得刷新凭证还需真实授权确认 |
| 访问令牌 `01:00:00` | 1 小时到期后应自动刷新，不应据此要求每小时重登 |
| 身份令牌 `00:05:00` | 不是论坛 API 会话只有 5 分钟；业务访问使用访问令牌 |
| 刷新令牌选择“滑动有效期” | 正常续期可更新有效窗口，不能据此承诺无限延长 |
| 固定有效期 `30.00:00:00` | 页面显示 30 天；它是否作为该客户端的绝对上限需站方确认 |
| 滑动有效期 `15.00:00:00` | 页面显示每次刷新获得 15 天窗口；实际策略仍受服务端约束 |
| “重用刷新令牌”未勾选 | 刷新会返回新凭证，客户端必须处理轮换并保存新值 |
| 应用尚未通过审核 | 页面明确提示授权时间和次数受限制 |
| 仅受信任应用可改令牌安全设置 | 延长或解除服务端限制不是当前客户端代码能完成的操作 |

截图反映页面状态，不能代替已保存配置、缓存更新和真实签发结果。若选项刚修改，应在后台提交保存并等待缓存生效；不需要先关闭用户确认、打开刷新令牌复用或放宽 PKCE。

常见 IdentityServer 实现中，滑动窗口不能超过绝对有效期，但本项目尚未确认 CC98 当前实现及未审核客户端的实际覆盖策略。[生命周期参考](https://docs.duendesoftware.com/identityserver/reference/v7/models/client/#refresh-token)

## App 如何保持登录

1. 使用系统 `ASWebAuthenticationSession` 打开官方授权页，每次生成独立 state 和 PKCE verifier。
2. 校验精确回调与 state，兑换授权码。请求 `offline_access` 并满足所需用户同意。[OpenID Connect 离线访问](https://openid.net/specs/openid-connect-core-1_0.html#OfflineAccess)
3. 用访问令牌读取官方 `/me`，确认实际账号；访问令牌、刷新令牌及到期信息按账号安全保存到 Keychain。App 不保存密码。
4. 冷启动、回到前台或请求前检查会话。访问令牌临近到期时，同一账号的请求等待同一次刷新，不各自消耗同一个刷新令牌。
5. 收到轮换凭证后，先保存新值再发布续期成功；迟到响应不能覆盖切换后账号或已更新凭据。刷新令牌轮换用于保护长期会话。[OAuth 安全要求](https://www.rfc-editor.org/rfc/rfc9700.html#section-4.14)
6. 网络错误保留凭据，恢复网络后重试；明确失效只要求对应账号重新授权，不删除该账号草稿、不切换身份代交业务请求。提交结果未知时不自动重发。

旧账号可能只有访问令牌。它在有效期内仍可使用；要继续长期使用，需完成一次新的授权取得刷新凭证。新授权也可能受服务器策略限制而未取得刷新凭证，应显示实际状态，不能宣称已经启用永久登录。

Keychain 仅属于当前设备与允许访问它的 App 身份。App 自签到期不等于 CC98 授权失效；重签换身份或卸载造成的数据／钥匙串访问变化，也不能用修改 token 解决。

## 仍需站方明确的事项

- **客户端审核与原生用途**：确认复用现有客户端支持原生 iOS 使用及未来分发方式。
- **实际签发条件**：确认该未审核客户端在请求 `offline_access` 并取得同意后，是否会签发可用刷新令牌，以及是否有额外的时间／次数限制。
- **长期刷新策略**：确认固定 30 天与滑动 15 天的实际含义，绝对上限、闲置到期、轮换和撤销规则；若希望持续数月免交互，需站方批准对应策略。
- **业务权限**：新增业务功能若需更多 scope，应单独确认；现有截图未展开 CC98 API 分组，不能据此判断所有论坛能力均已授权。

这些条件不阻止先验证当前授权与自动续期，但决定可承诺的长期使用期限。App 不绕过站方到期、撤销或权限检查。

## 验收与独立功能

真实系统授权、首次取得刷新凭证、跨有效期续期、网络恢复、多账号与重签安装，按 [真机验证清单](DEVICE_TEST_CHECKLIST.md) 记录。云端合成测试不使用论坛账号，也不证明真实令牌已签发或站方审核已完成。

问号仍是独立接入：本轮不改变其服务端会话，不自动沿用论坛刷新令牌。若以后接入，需按问号服务的 challenge、ID Token 验证、用户同意和账号历史连续性单独实现。
